Daily Brief — infrastructure plan

Rule-based (no AI) 7am + noon briefing, delivered by “Bruno” on Telegram + email. Revision 4 · private GitHub repo · target cost $0, ceiling a couple dollars a month.

Runs onGitHub Actions cron in a private repo. Nothing of yours needs to be awake.
ReadsGoogle Calendar (incl. the Canvas feed) and Gmail, read-only.
Delivers viaTelegram bot (free, instant) with the full version by email. iMessage stays optional.
Cost$0. Telegram, GitHub Actions and Gmail/Calendar APIs are all free at this volume.

1. Architecture

The job is stateless. “State” (when the last brief went out) is read back from Gmail itself, so there is no database to host, secure or lose.

2. Delivery: Telegram bot, in Bruno's voice

Decision: deliver through a Telegram bot. It is free, delivers instantly to your phone, needs no phone to be on at a particular time, and setup is three steps (create the bot with @BotFather, message it once, store two secrets). The full brief still goes to your email, so nothing depends on Telegram alone. If one channel fails the other still sends and the email says what broke.

2b. Bruno's voice: phrase bank, still no AI

  • The persona name (Bruno, or Jarvis) and your name live in [persona] in config.toml.
  • All wording is in phrases.toml: ~16 banks (morning/noon greetings, “needs attention” lead-ins, all-clear lines, section intros, sign-offs), 4–7 variants each, with {name}, {bot} placeholders. Add lines any time.
  • Pick rule: pseudo-random but seeded by date + slot, so a re-run of the same brief reads identically, and the same phrase is never used twice in a row (the last pick per bank is kept in state). Tested over 30 simulated days.
  • Data lines (amounts, dates, subjects) are never reworded; only the framing around them varies.

New behavior this enables

  • Unpaid-bill ledger (fixes problem #4): the job looks back 40 days for “payment due” notices and keeps each on the list until a later “payment received” from the same biller settles it. Items due within 3 days (or overdue) go under Needs attention, later ones under Upcoming payments.
  • Noise cut: about 25 Chase balance emails in 6 months become one line; promos from banks and carriers disappear.
  • Known gaps: the rent notice has no amount; Mercury has no due date; lease/e-sign emails (“Document is Ready to Sign”) are not bills, so they only surface if Gmail marks them important. Due dates that live only in HTML buttons or PDFs cannot be read.
  • Billers not visible in this inbox (internet, car loan, tuition, other cards) need a block added when their first notice shows up; the README explains how.

3c. Multiple Gmail accounts

  • Design: [[accounts]] in config; one OAuth client, one refresh token per login (GOOGLE_REFRESH_TOKEN, _2, _3 secrets). Mail, calendars and the bill ledger are collected per account, merged, and tagged [name] in the brief.
  • Sending: the brief is sent from one account (send_from = true) to your inbox; the others only need read access.
  • Dedupe: a calendar shared across logins shows each event once.
  • Isolation: if one login's token is revoked, that account appears as ACCOUNT … under Needs attention and the others still report.
  • Setup cost: run auth_setup.py once per account, signing in as that account; each extra Gmail must be a test user or the consent screen must be published.
  • Not done yet: the only Gmail I could read was zshake21@gmail.com. Biller rules for your other accounts need that mail sampled, or you can tell me which senders to expect.

3d. State (kept in the private repo)

  • The workflow keeps a small state.json on a separate brief-state branch, so it never clutters your code history. It is committed back after each real send.
  • It holds: when the last brief went out, ids of mail already reported (pruned after 7 days), the last phrase used per bank, and a 30-entry log of how late each run started.
  • What that buys: catch-up (a missed or late run's mail appears in the next brief, up to 3 days back), no repeats of the same email, non-repeating phrases, and measured lateness of GitHub's scheduler so you can judge it with data.
  • It stores message ids and timestamps only, no subjects or bodies.

4. Hosting & scheduling: can GitHub do the 7am and noon triggers?

Yes. One workflow, cron: "17 14,15,19,20 * * *", fires at 7:17 and 12:17 Pacific in both daylight and standard time (7am = 14/15 UTC, noon = 19/20 UTC); the off-season twin sees it is outside a slot and exits. Minute 17 sidesteps the top-of-hour rush.

Why I called it “not great”: GitHub treats scheduled runs as best-effort. They can start late when GitHub is busy and, rarely, be skipped (GitHub docs). Public repos also get schedules switched off after 60 days of inactivity (ref); yours is private. It is fine for a briefing, but not to-the-minute. The design absorbs it:
  • 1-hour grace window: a run that starts up to an hour late still sends; a later one is skipped rather than duplicated.
  • State-based catch-up: if a brief is missed entirely, the next one includes the missed mail.
  • The state log records how late each run starts. After two weeks you will know if it is a real problem.
  • If it is: add a free external pinger (e.g. cron-job.org) that calls the workflow's workflow_dispatch at exactly 7:00 and 12:00 PT. Trade-off: a GitHub token stored at a third party. Or move the trigger to a Cloudflare Workers cron (free, more punctual).
  • Still to build: the watchdog that alerts you when a brief did not go out at all.

5. Auth, secrets & privacy

  • Google scopes: calendar.readonly, gmail.readonly, gmail.send. It cannot modify or delete anything. Consent screen must be In production, and you authorize after publishing, or tokens die in 7 days (ref).
  • Secrets (GitHub Actions only): Google client id/secret, one refresh token per Gmail account, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID.
  • Private repo: required, since dry-run logs print the brief. The workflow has contents: write solely to update the state branch.
  • Telegram: messages to a bot are stored on Telegram's servers (not end-to-end encrypted). Health items are reduced to a count there; bills still show amounts. Turn on telegram_redact_health (default) or move amounts to email only if that bothers you.
  • Only your own chat id can receive messages; the bot token is never printed.

7. Money & banks

Credit-card and bill emails already provide amount due, due date and fraud alerts, so no bank connection is needed for the brief. If you later want balances, SimpleFIN Bridge is read-only (cannot move money), refreshes about daily, and is published at roughly $15/yr — their pages disagree on price structure, so confirm. It is deliberately not in the first release.
