Daily Brief — infrastructure plan

Rule-based (no AI) 7am + noon briefing, delivered to iMessage. Revision 3 · private GitHub repo · target cost $0, ceiling a couple dollars a month.

Runs onGitHub Actions cron in a private repo. Nothing of yours needs to be awake.
ReadsGoogle Calendar (incl. the Canvas feed) and Gmail, read-only.
Delivers viaEmail + push now; iMessage through an iPhone Shortcut bridge (free) or a paid iMessage API (optional).
Cost$0 baseline. $4.99 one-time for guaranteed push. iMessage-as-a-service is the only thing that breaks the budget.

1. Architecture

The job is stateless. “State” (when the last brief went out) is read back from Gmail itself, so there is no database to host, secure or lose.

2. Delivery: iMessage is the hard part

Fact: Apple has no iMessage API, and there is no free way to send a real iMessage from a cloud server. Every server-side option is either a third-party service running real Apple hardware, or something on your iPhone/Mac. Recommendation

  2. Also send a short, plain-text “iMessage email” with a fixed subject prefix; build the Shortcut (Automation → Email → sender = yourself, subject contains prefix → Run Immediately → Send Message). Test for a week.
  3. If the Shortcut can't run silently or can't text yourself, decide between living with push, SMS (E), or paying for F.

Format constraint: iMessage is a chat, not a document. I'll add a second renderer capped near 1,000 characters: Needs attention first, then next 3 events, then counts (“4 new mail, 2 bills”), with the full detail in the email.

3. Homework: the Canvas calendar feed

You're right: the Canvas feed subscribed in Google Calendar is the most reliable homework source, and it carries course, title, due time and link. So I'm changing the design, not just the keywords:

  • Add homework_calendars = ["<name of your Canvas calendar>"] to config.toml. Every event on that calendar is treated as an assignment — no guessing from words. The keyword regex remains only for your normal calendars.
  • Parse the course tag from the title (Canvas appends [COURSE]) and group the homework section by course, sorted by due time, with “due in 3h / tomorrow 11:59pm” phrasing.
  • Surface overdue-today and due-within-24h items under Needs attention.
  • Caveat: Google refreshes subscribed (ICS) calendars on its own schedule, so newly posted assignments can appear hours late. Nothing we run can speed that up; the brief shows whatever Google has.
  • Assumption to check: subscribed calendars are readable through the Calendar API like any other calendar. I expect so, but I'll confirm during the first dry run.

New behavior this enables

  • Unpaid-bill ledger (fixes problem #4): the job looks back 40 days for “payment due” notices and keeps each on the list until a later “payment received” from the same biller settles it. Items due within 3 days (or overdue) go under Needs attention, later ones under Upcoming payments.
  • Noise cut: about 25 Chase balance emails in 6 months become one line; promos from banks and carriers disappear.
  • Known gaps: the rent notice has no amount; Mercury has no due date; lease/e-sign emails (“Document is Ready to Sign”) are not bills, so they only surface if Gmail marks them important. Due dates that live only in HTML buttons or PDFs cannot be read.
  • Billers not visible in this inbox (internet, car loan, tuition, other cards) need a block added when their first notice shows up; the README explains how.

3c. Multiple Gmail accounts

  • Design: [[accounts]] in config; one OAuth client, one refresh token per login (GOOGLE_REFRESH_TOKEN, _2, _3 secrets). Mail, calendars and the bill ledger are collected per account, merged, and tagged [name] in the brief.
  • Sending: the brief is sent from one account (send_from = true) to your inbox; the others only need read access.
  • Dedupe: a calendar shared across logins shows each event once.
  • Isolation: if one login's token is revoked, that account appears as ACCOUNT … under Needs attention and the others still report.
  • Setup cost: run auth_setup.py once per account, signing in as that account; each extra Gmail must be a test user or the consent screen must be published.
  • Not done yet: the only Gmail I could read was zshake21@gmail.com. Biller rules for your other accounts need that mail sampled, or you can tell me which senders to expect.

5. Auth, secrets & privacy

  • Scopes: calendar.readonly, gmail.readonly, gmail.send. It cannot modify or delete anything.
  • The OAuth consent screen must be In production; “Testing” refresh tokens expire after 7 days, and tokens issued before publishing keep that limit, so authorize after publishing (ref). Gmail scopes are “restricted”; a one-user unverified app shows a warning screen but is intended to work — I'll confirm on first run.
  • Secrets live only in GitHub Actions secrets: Google client id/secret/refresh token, Pushover keys. Private repo is required because dry-run logs print mail subjects.
  • Logs will print counts and categories only, never subjects or bodies, on scheduled runs.

7. Money & banks

Credit-card and bill emails already provide amount due, due date and fraud alerts, so no bank connection is needed for the brief. If you later want balances, SimpleFIN Bridge is read-only (cannot move money), refreshes about daily, and is published at roughly $15/yr — their pages disagree on price structure, so confirm. It is deliberately not in the first release.
